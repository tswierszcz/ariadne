# Supported capabilities and limitations

This document describes the current implementation of Ariadne. Future requirements live in [RECOMMENDATION](../RECOMMENDATION/README.MD); their presence does not mean a feature is available.

Last source review: 2026-10-15. This initial inventory is based on repository source inspection. Tests and live analyses were not run to produce this inventory. Links to test files identify existing verification material, not new passing results. Future implementation sessions must record the checks they actually perform.

## Reading the status

- **Implemented:** the specific behavior described is present; the label does not cover every variation of the mechanism.
- **Partial:** a defined subset exists, with material gaps listed.
- **Experimental:** available behavior undergoing qualification, with its conditions stated.
- **Not implemented:** the current pipeline does not provide that behavior.
- **Unassessed:** evidence is insufficient to state the current scope.

Implementation status, tested versions and evidence quality are separate. A completed design phase does not change product support.

## Bytecode, graph and framework knowledge

| Capability | Status | Available scope and conditions | Limits and evidence |
|---|---|---|---|
| Pure-Go class parsing and invoke extraction | Implemented | Reads the supported classfile structures and extracts implemented invoke instructions without running a JDK. | Java 8/21 fixture JARs exist; this is not qualification of every compiler, language feature or JVM version. [Parser](../internal/classfile/classfile.go), [calls](../internal/classfile/calls.go), [tests](../internal/classfile/classfile_test.go). |
| Direct calls, CHA and inheritance | Partial | Direct symbolic edges and CHA subtype expansion are now exact-descriptor, not name-only (JVM_GRAPH G2): two overloads of the same name no longer get conflated into each other's CHA edges, and a direct call whose declared receiver type only inherits the method (never overriding it) is led to the class that actually supplies the body (`hierarchy.ResolveExact`/`callgraph.resolveTarget`) instead of a dead-end node under the subclass's own name. Each edge also carries a resolution basis (`direct`/`cha`/`synthetic`) and the bytecode offset(s) of the call site(s) that produced it, surfaced in the report's entry-call line and `results.json`'s `entry.kind`/`entry.basis`/`entry.pc`. Vulnerable-method matching ([matching](../internal/reach/match.go)) stays overload-insensitive by necessity, since vulnmap sources never carry a descriptor. | JDK-prefix expansion is still skipped, so CHA itself never expands into the JDK; a method actually inherited from a class outside the analyzed input (the JDK or anything not in `-app`/`-deps`) still cannot be resolved further and reports as `Graph.UnresolvedOwnerCount()` — a large, expected, informational number, not a correctness signal on its own (see that function's own doc comment). Measured effect on real petclinic/WebGoat runs: CHA edge count dropped sharply (overload conflation was adding a lot of spurious edges) and at least one CVE's status corrected from a false `FRAMEWORK` (a CHA-artifact path through Spring WebFlux's reactive multipart reader, which petclinic's classic Spring MVC stack never actually uses) to `NOT_REACHABLE`. [Builder](../internal/callgraph/build.go), [graph](../internal/callgraph/graph.go), [resolve](../internal/hierarchy/resolve.go), [skip](../internal/callgraph/skip.go), [matching](../internal/reach/match.go), [entry edge](../internal/reach/reach.go). |
| Duplicate class selection | Partial | Keeps one definition — the first in explicit input order (app, then dependency jars in the order given), never whichever parallel read happened to finish first — and reports every duplicate as structured evidence (`Hierarchy.Duplicates()`: kept/shadowed jar path and SHA-256 content hash) as well as a warning string. Verified on real petclinic/WebGoat runs (dozens of real duplicate classes, e.g. `jakarta.activation-*` jars) that repeated runs select the same class and produce byte-identical `results.json`. | Full loader isolation is absent — one FQCN still maps to exactly one class across the whole analysis, not per-loader; classpath order is assumed from input list order, which may not match a real JVM's actual classloading order at runtime. [Hierarchy build](../internal/hierarchy/build.go), [duplicates](../internal/hierarchy/duplicates.go). |
| Implicit class initialization | Partial | `new`/`getstatic`/`putstatic`/`invokestatic` now add an edge to the target class's own `<clinit>` when it has one (JVM_GRAPH G3), including through field/method inheritance (`hierarchy.ResolveField`/`ResolveExact`) and a class's own `<clinit>` requiring its superclass's `<clinit>` first (JVMS 5.5). `-roots profile`'s `roots.main` also adds the entry class's `<clinit>` as a root directly (the JVM runs it before `main`, not because of any instruction inside `main` itself); `-roots all` already had this for free. `Graph.InitEdgeCount()`/the report's "class-init" figure give the edge count. | A class-literal (`Foo.class`, `ldc`) never triggers initialization, correctly; a getstatic/putstatic that is actually a compile-time constant never reaches this code at all, since javac/kotlinc inline those as `ldc` rather than emit getstatic/putstatic — ariadne does not need to separately detect field constant-ness. Not modeled: initialization order/timing, the narrower default-method superinterface-eager-init rule (JVMS 5.5), and reflection-driven initialization (`Class.forName`). Measured on real petclinic/WebGoat: tens of thousands of real edges added, but none changed any CVE's status in either app's current baseline. [Calls](../internal/classfile/calls.go), [builder](../internal/callgraph/build.go), [resolve](../internal/hierarchy/resolve.go), [roots](../internal/profile/profile.go). |
| Multi-release target selection | Partial | `-target-java N` (JVM_GRAPH G4) selects, for a jar whose manifest declares `Multi-Release: true`, the highest `META-INF/versions/<V>/...` variant with `V <= N` per class, falling back to the base entry; without the flag, every jar's base classes are read regardless of any `META-INF/versions/` present — the documented fallback, not a guess from the highest bytecode version seen. The selected entry's zip path and variant version are kept per class (`ClassInfo.SourceEntry`/`VariantVersion`). Verified on real petclinic/WebGoat: `-target-java 17` activates 15/21 real variants respectively (8 genuinely multi-release dependency jars identified in petclinic alone, e.g. `log4j-api`, `byte-buddy`, `h2`), with no change to either app's CVE statuses in the current baseline. | A jar not declaring `Multi-Release: true` never treats `META-INF/versions/` as active, even with a target set (correct per the JAR File Specification). A malformed version directory (non-numeric, or below the JAR spec's minimum of 9) is skipped with a warning, not guessed at. Initialization order/timing and the CVE F8a target-description contract are out of this phase's scope ("pełny adapter podatności JDK nie jest wymagany"). [JAR reader](../internal/hierarchy/jarread.go), [CLI](../cmd/ariadne/main.go). |
| Lambdas and method references | Partial | Call-graph level (JVM_GRAPH): recognizes LambdaMetafactory/altMetafactory implementation handles, adding a direct target at creation. Value level (DYNAMIC_LINKAGE L0/L1, new): `internal/dataflow` now produces a real `valueflow.KindFunctional` value for a resolved lambda/method reference — its functional interface/method (e.g. `java.lang.Runnable`/`run`), its own implementation method (owner/name/desc, resolved once via the bootstrap, never through CHA), the implementation's JVMS 5.4.3.5 `MethodHandle` reference kind (`classfile.RefInvokeStatic` and the now-complete rest of that table), and every captured free variable as its own already-resolved `Value` — instead of the generic `KindUnknown` every other call's return value gets. ASYNC_CALLBACKS A1/A2 consume this directly: a lambda/method reference passed as a `Thread`/`Executor` callback argument resolves straight to its implementation method and gets a real call-graph edge, no longer stopping at "unresolved, needs DYNAMIC_LINKAGE L1". Verified on real petclinic/WebGoat: 0 errors/panics building this value across ~500k methods; closing this gap raised ASYNC_CALLBACKS' own resolved-identity count from 53/35 to 69/46 (of 135/134 cataloged sites). | Still creation-site-only: no virtual/bound-instance method-reference receiver modeling (`obj::method`), no `MethodHandle` constant/invocation beyond what LambdaMetafactory already resolves (DYNAMIC_LINKAGE L2+), and other bootstraps (`StringConcatFactory` and the like) are still `KindUnknown`, not modeled. [Calls](../internal/classfile/calls.go), [bootstrap](../internal/classfile/bootstrap.go), [local-op decode](../internal/classfile/localops.go), [value construction](../internal/dataflow/step.go), [value domain](../internal/valueflow/value.go). |
| General reflection, MethodHandle invocation and custom bootstrap models | Not implemented | API calls can appear as ordinary symbolic calls. | No general reconstruction of reflective targets, handle adaptations or arbitrary bootstrap results. [Calls](../internal/classfile/calls.go). |
| Profiles and selected roots | Implemented | Auto-detection/merging and explicit profiles: spring, servlet, jakarta, micronaut, quarkus, generic; `-roots all` or `profile`. | This is profile knowledge, not full runtime framework emulation. [Profile code](../internal/profile/profile.go), [profile tests](../internal/profile/profile_test.go). |
| Spring Data synthetic dispatch | Partial | The active profile can connect declared subtype methods of Repository to same-named SimpleJpaRepository methods. | A narrow bridge; not complete support for every repository, inherited operation, proxy or AOP chain. [Synthetic edges](../internal/callgraph/synthetic.go), [Spring profile](../internal/profile/profiles/spring.yaml). |
| Annotation names | Partial | Reads implemented runtime-visible class/method/parameter annotation names for profiles. | Values are discarded; constructor synthetic parameter alignment has a documented gap. [Annotations](../internal/classfile/annotations.go). |
| DI/AOP/configuration execution models | Not implemented | Existing annotations, profiles and the narrow Spring Data bridge supply some static hints. | No general bean binding, pointcut, active-environment, web.xml or configuration-driven execution model. [Profile](../internal/profile/profile.go). |
| ServiceLoader and JPMS service models | Partial | SERVICE_LOADING S0–S2. S0: `internal/serviceload.Inventory` parses every `META-INF/services/<Interface>` file across the app and dependency jars and cross-references each declared provider class against the analyzed hierarchy. S1: `internal/serviceload.FindLoadSites` finds every `ServiceLoader.load(...)`/`loadInstalled(...)` call site and resolves the service-interface `Class` argument via DATA_FLOW D0-D2's local-value analysis, distinguishing which loader was used. S2: `internal/serviceload.FindMaterializations`/`EdgeTargets` + `internal/callgraph.ApplyServiceLoaderEdges` add, for every interface actually resolved at some call site, a real call-graph edge from that call site to each registered provider's public no-argument constructor (plus a related edge to the provider's own `<clinit>` if it has one) — a new `BasisServiceLoader` edge basis, distinct from a profile's `BasisSynthetic` proxy guess. A provider the found interface was never used for gets no edge (not a gap); a found, used provider with no public no-arg constructor gets an explicit, reported gap instead of a fabricated edge. Each phase has its own report table ("ServiceLoader provider registrations" / "ServiceLoader.load call sites" / "ServiceLoader provider constructors modeled"). Verified on real petclinic/WebGoat: 44/158 registrations (S0); 29/48 `load()` call sites with 13/31 resolved to a real interface (S1); 8/147 providers modeled as real constructor targets with 10/158 edges added (S2, including the related `<clinit>` edges) — e.g. `org.hibernate.jpa.HibernatePersistenceProvider#<init>()V` reachable from the `javax.persistence.spi.PersistenceProvider` call site. Reachability counts (REACHABLE/FRAMEWORK/NOT_REACHABLE/UNKNOWN) on both apps are **unchanged** by S2 on this baseline (the newly-reachable provider constructors don't themselves lead to any CVE's vulnerable method on these two apps), confirmed with byte-identical `results.json` across two offline runs. | **Still only the constructor itself** — no iterator/`Provider.get` method call on the resulting provider instance is modeled (that part of S2's own scope), and JPMS `module-info`'s `uses`/`provides` are not read at all (S3). A caller-named `ClassLoader`/`ModuleLayer` is not verified to actually see the same providers a classpath `META-INF/services` registration was found under — S2 connects them anyway (the same over-approximate-rather-than-silently-drop choice the rest of ariadne makes), so this is a known, documented imprecision, not a silent assumption. [Parser](../internal/serviceload/parse.go), [inventory](../internal/serviceload/inventory.go), [load-site resolution](../internal/serviceload/loadsites.go), [materialization](../internal/serviceload/materialize.go), [graph edges](../internal/callgraph/serviceloader_edges.go), [resource listing](../internal/input/serviceresources.go). |
| General callbacks and asynchronous execution models | Partial | ASYNC_CALLBACKS A0–A2. A0: `internal/callback.FindRegistrationSites` inventories every call site matching a small, hand-picked catalog of JDK callback-registration APIs (`Thread`'s Runnable-taking constructors, `Executor`/`ExecutorService#execute`/`#submit`) across the app and dependencies, skipping `classfile.CallDynamic` entries (a method reference's *resolved implementation* can coincidentally share a cataloged signature without being a real call — caught as a real false positive on petclinic and fixed). A1: `internal/callback.ResolveCallbacks` resolves each cataloged site's callback argument to a concrete class via DATA_FLOW D0-D2's local-value analysis, when it was a direct `new` allocation. A2: `internal/callback.FindCallbackEdges` + `internal/callgraph.ApplyCallbackEdges` add a real call-graph edge (`BasisCallback`, a "may run" edge like a profile's synthetic edge — never claiming the registration call itself guarantees execution, and never inventing a thread identity) from the registration site to the class that actually declares the callback method (ordinary JVM method resolution up the superclass chain), with an explicit, reported gap when that resolution fails (normally only because a class on that chain — e.g. a JDK class like `FutureTask` — isn't part of the analyzed hierarchy). Each phase has its own report table. Verified on real petclinic/WebGoat: 137/140 registration call sites (A0); after DYNAMIC_LINKAGE L0/L1 closed the lambda gap, 69/46 of 135/134 resolved to a real concrete class or a lambda/method reference's own implementation method (A1, e.g. `ch.qos.logback.core.net.AbstractSocketAppender$1#run` for a `new`, `CommonsObjectPool2Metrics#lambda$registerNotificationListener$1` directly for a lambda); 67/44 of those modeled as real call-graph edges with 2 genuine, correctly-reported gaps on petclinic (`org.springframework.util.concurrent.ListenableFutureTask`'s `run()` is inherited from the JDK's own `FutureTask`, outside ariadne's analyzed universe — a lambda/method-reference identity never has this kind of gap, since it needs no further hierarchy resolution) (A2). Reachability is unaffected by all three phases on both apps, confirmed unchanged, byte-identical `results.json`/`report.md` across two offline runs. | **Still only the registration→callback-method edge** — no interprocedural summaries inside the callback body itself beyond what the rest of the call graph already models, no `CompletionStage`/future chaining, listeners, or reactive operators (ASYNC_CALLBACKS A3's own scope). The "Thread subclass overrides `run()` directly, no Runnable object anywhere" pattern is not detected at all (A0's catalog only matches Runnable-taking constructors). Catalog covers only `Thread`/`Executor`/`ExecutorService`. [Catalog](../internal/callback/catalog.go), [inventory](../internal/callback/sites.go), [identity resolution](../internal/callback/identity.go), [graph edges](../internal/callback/edges.go). |
| RTA and points-to | Not implemented | Current builder uses CHA with configured skip behavior. | No allocation-driven RTA or receiver-specific points-to analysis. [Builder](../internal/callgraph/build.go). |
| Data flow and taint | Partial | DATA_FLOW D0–D2. D1: `classfile.BuildCFG` builds a real control-flow graph from any method's bytecode — basic blocks, fall-through/branch/exceptional edges (exception table parsed, JVMS 4.7.3), resolved branch/switch targets (JVMS 6.5), and `ArgumentSlots` for descriptor-driven local-variable slot widths. `jsr`/`ret` is recognized and marked unsupported rather than modeled or crashed on. D2: `internal/dataflow.Analyze` runs a real, width-correct abstract interpreter over that CFG — full operand-stack simulation including the whole dup/dup2/pop/pop2/swap family (JVMS 6.5, category-1/2-aware) — and produces real `valueflow.Value` facts: string/class constants propagate through local variables and branch joins (merging to a `KindSet`, or widening to `KindUnknown` with a reason past the merge budget), call arguments are exposed per call site via `valueflow.Facts.ArgumentAt`. Arithmetic/conversion/comparison results are deliberately left `KindUnknown` (D2's own declared scope is string/class literals, not numeric values) while still keeping the stack shape correct for everything after them. A stack-shape inconsistency at a control-flow join (never expected on valid bytecode) or a `jsr`/`ret` subroutine makes the analysis report itself `Aborted` with a reason, never panic or guess. Verified at scale: 0 errors/panics running the full abstract interpreter over all ~219k (petclinic) / ~280k (WebGoat) real methods with code, with the same 2/96 real jsr/ret methods as D1 correctly flagged as aborted and nothing else. | **Nothing in the actual pipeline calls `dataflow.Analyze` yet** — it is tested and correct but not wired into `cmd/ariadne`/`internal/reach`/`internal/serviceload`, so it changes no user-visible behavior today. No interprocedural summaries (D3 — a call's return value is always `KindUnknown`), no taint (D4). `SERVICE_LOADING:S1` (resolving `ServiceLoader.load`'s `Class` argument) is the first planned consumer. [Code parser](../internal/classfile/code.go), [CFG builder](../internal/classfile/cfg.go), [per-instruction decoder](../internal/classfile/localops.go), [D2 analyzer](../internal/dataflow/analyze.go), [IR contract](../internal/bytecodeir/site.go), [value domain](../internal/valueflow/value.go). |

## Interpretation and maintenance

`NOT_REACHABLE` means no path was found under the implemented model and chosen roots. It is not a guarantee that the application is safe. `NOT_APPLICABLE` identifies the implemented WebJar-only case; browser vulnerabilities may still matter. A profile match, configured registration, static path, LLM opinion and runtime observation are different evidence types.

The source inventory above does not claim fresh test passes or new live runs. For future changes, attach the actual test/scenario evidence and update exact supported subsets, versions, flags and limitations. Update README and report limitations when their claims change; preserve unsupported cases in the description. Phase progress belongs in [IMPLEMENTATION_STATUS.MD](../RECOMMENDATION/IMPLEMENTATION_STATUS.MD).
