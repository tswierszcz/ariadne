# Supported capabilities and limitations

This document describes the current implementation of Ariadne. Future requirements live in [RECOMMENDATION](../RECOMMENDATION/README.MD); their presence does not mean a feature is available.

Last source review: 2026-10-15. This initial inventory is based on repository source inspection. Tests and live analyses were not run to produce this inventory. Links to test files identify existing verification material, not new passing results. Future implementation sessions must record the checks they actually perform.

## Reading the status

- **Implemented:** the specific behavior described is present; the label does not cover every variation of the mechanism.
- **Partial:** a defined subset exists, with material gaps listed.
- **Experimental:** available behavior undergoing qualification, with its conditions stated.
- **Not implemented:** the current pipeline does not provide that behavior.
- **Unassessed:** evidence is insufficient to state the current scope.

Implementation status, tested versions and evidence quality are separate. A completed design phase does not change product support.

| Pure-Go class parsing and invoke extraction | Implemented | Reads the supported classfile structures and extracts implemented invoke instructions without running a JDK. | Java 8/21 fixture JARs exist; this is not qualification of every compiler, language feature or JVM version. | Direct calls, CHA and inheritance | Partial | Direct symbolic edges and CHA subtype expansion are now exact-descriptor, not name-only (JVM_GRAPH G2): two overloads of the same name no longer get conflated into each other's CHA edges, and a direct call whose declared receiver type only inherits the method (never overriding it) is led to the class that actually supplies the body (`hierarchy.ResolveExact`/`callgraph.resolveTarget`) instead of a dead-end node under the subclass's own name. Each edge also carries a resolution basis (`direct`/`cha`/`synthetic`) and the bytecode offset(s) of the call site(s) that produced it, surfaced in the report's entry-call line and `results.json`'s `entry.kind`/`entry.basis`/`entry.pc`. Measured effect on real petclinic/WebGoat runs: CHA edge count dropped sharply (overload conflation was adding a lot of spurious edges) and at least one CVE's status corrected from a false `FRAMEWORK` (a CHA-artifact path through Spring WebFlux's reactive multipart reader, which petclinic's classic Spring MVC stack never actually uses) to `NOT_REACHABLE`. [Calls](../internal/classfile/calls.go), [builder](../internal/callgraph/build.go), [resolve](../internal/hierarchy/resolve.go), [roots](../internal/profile/profile.go). |
| Multi-release target selection | Partial | `-target-java N` (JVM_GRAPH G4) selects, for a jar whose manifest declares `Multi-Release: true`, the highest `META-INF/versions/<V>/...` variant with `V <= N` per class, falling back to the base entry; without the flag, every jar's base classes are read regardless of any `META-INF/versions/` present — the documented fallback, not a guess from the highest bytecode version seen. The selected entry's zip path and variant version are kept per class (`ClassInfo.SourceEntry`/`VariantVersion`). Verified on real petclinic/WebGoat: `-target-java 17` activates 15/21 real variants respectively (8 genuinely multi-release dependency jars identified in petclinic alone, e.g. `log4j-api`, `byte-buddy`, `h2`), with no change to either app's CVE statuses in the current baseline. | A jar not declaring `Multi-Release: true` never treats `META-INF/versions/` as active, even with a target set (correct per the JAR File Specification). A malformed version directory (non-numeric, or below the JAR spec's minimum of 9) is skipped with a warning, not guessed at. Initialization order/timing and the CVE F8a target-description contract are out of this phase's scope ("pełny adapter podatności JDK nie jest wymagany"). [JAR reader](../internal/hierarchy/jarread.go), [CLI](../cmd/ariadne/main.go). |

Verified on real petclinic/WebGoat: 0 errors/panics building this value across ~500k methods; closing this gap raised ASYNC_CALLBACKS' own resolved-identity count from 53/35 to 69/46 (of 135/134 cataloged sites). | Still creation-site-only: no virtual/bound-instance method-reference receiver modeling (`obj::method`), no `MethodHandle` constant/invocation beyond what LambdaMetafactory already resolves (DYNAMIC_LINKAGE L2+), and other bootstraps (`StringConcatFactory` and the like) are still `KindUnknown`, not modeled. | General callbacks and asynchronous execution models | Partial | ASYNC_CALLBACKS A0–A2. A0: `internal/callback.FindRegistrationSites` inventories every call site matching a small, hand-picked catalog of JDK callback-registration APIs (`Thread`'s Runnable-taking constructors, `Executor`/`ExecutorService#execute`/`#submit`) across the app and dependencies, skipping `classfile.CallDynamic` entries (a method reference's *resolved implementation* can coincidentally share a cataloged signature without being a real call — caught as a real false positive on petclinic and fixed). | Data flow and taint | Partial | DATA_FLOW D0–D3 (three slices). D1: `classfile.BuildCFG` builds a real control-flow graph from any method's bytecode. D2: `internal/dataflow.Analyze` runs a real, width-correct abstract interpreter over that CFG — full operand-stack simulation (JVMS 6.5, category-1/2-aware dup/pop) — producing real `valueflow.Value` facts: string/class constants, allocations, lambdas/method handles (see their own rows), exposed via `valueflow.Facts.ArgumentAt`/`ReceiverAt`. This is now the live engine behind SERVICE_LOADING, ASYNC_CALLBACKS, and DYNAMIC_LINKAGE's own rows below — no longer an unconsumed contract. D3 static-field slice: a `getstatic` of a static field now identifies *which* field it read (`valueflow.KindField`), and `internal/dataflow.ResolveStaticField` finds every write of that field *within its own declaring class* (via the already-extracted `InitPutStatic` references) and merges their values into one summary — the first genuinely interprocedural fact D2 alone couldn't produce (a value crossing from one method into another through a field, not a parameter or return value). D3 instance-field slice: `getfield` produces the same `KindField` value a static read does, and `internal/dataflow.ResolveInstanceField` covers the one instance-field shape safe to resolve without real points-to — a *final* field written only by a provable `this.field = ...` store inside a constructor. `internal/dataflow.ResolveField` dispatches between static/instance by the field's real access flags, decided once. D3 call-result slice (new): an `invokestatic`/`invokespecial` call — never a virtual/interface call, whose real target depends on the receiver's runtime type (CHA ambiguity a summary here would silently paper over) — now identifies *which* method it called (`valueflow.KindCallResult`), and `internal/dataflow.ResolveCallResult` resolves the exact declaring class (`hierarchy.ResolveExact`, shared with JVM_GRAPH G2) and merges every value-returning `return` site it finds, in deterministic PC order (`MethodFacts.returnOrder`, never Go's randomized map order). A field's resolved value and a call's resolved value can each turn out to be the other kind (a field initialized from a call; a getter returning a cached field) — `chaseFieldOrCall` follows either one more hop, sharing one visited set across both so a chain crossing between them stays cycle-safe (DATA_FLOW D0's own "recursion converges or reveals a limit"), never looping forever on mutual recursion. Verified with real cross-method merge tests (`TestMergeFieldWriters_*`, `TestMergeConstructorFieldWriters_*`, `TestMergeReturns_*`, `TestResolveField_dispatchesByAccessFlagsNotTrialAndError`, `TestChaseFieldOrCall_*`) and wired as `internal/methodhandle`'s own second-chance resolution step. | **All three D3 slices' own measured effect on the two real control apps is honestly zero new call-graph edges**, but each slice changed *what gets reported*, not just added an unused code path: the field/call dispatcher fix caught a real diagnostic bug (a static field's own failure reason getting masked by an unrelated instance-field message), and the shared chase now resolves petclinic's one field-backed `MethodHandle` receiver all the way through to its true root cause (a non-literal `findVirtual` argument) instead of stopping at an intermediate "field write not found". On WebGoat, the real instance-field receivers (10/46) are genuine but **not final** (JRuby's handle-caching fields are lazily reassigned) — correctly declined, not guessed at; several others now surface as calls into `java.lang.invoke.MethodHandles` itself, outside the analyzed hierarchy (a JDK class, never read). Arithmetic/conversion/comparison results are still deliberately `KindUnknown`. No taint (D4), no non-final instance-field tracking (needs real points-to), no virtual-call return-value summaries (would need CHA-aware merging across every override), no versioning/invalidation. ## Interpretation and maintenance

`NOT_REACHABLE` means no path was found under the implemented model and chosen roots. It is not a guarantee that the application is safe. `NOT_APPLICABLE` identifies the implemented WebJar-only case; browser vulnerabilities may still matter. A profile match, configured registration, static path, LLM opinion and runtime observation are different evidence types.

The source inventory above does not claim fresh test passes or new live runs. For future changes, attach the actual test/scenario evidence and update exact supported subsets, versions, flags and limitations. Update README and report limitations when their claims change; preserve unsupported cases in the description. Phase progress belongs in [IMPLEMENTATION_STATUS.MD](../RECOMMENDATION/IMPLEMENTATION_STATUS.MD).
